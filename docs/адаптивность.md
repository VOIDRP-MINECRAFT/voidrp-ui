# Адаптивность

Страница верстается под экран игрока, а не под один придуманный размер. Здесь — как это
устроено, что писать в коде страницы и почему один кусок всё-таки приходится спросить у
самого игрока.

## Холст

Высота холста всегда **1024 единицы** — это вся высота окна игрока, при любом разрешении и
любом масштабе интерфейса. Единица квадратная, поэтому ширина холста зависит от формы
экрана:

| Экран | Ширина холста |
|---|---|
| 5:4 (1280×1024) | 1280 |
| 4:3 | 1365 |
| 16:10 | 1638 |
| 16:9 | 1820 |
| 21:9 | 2389 |

Ничего не растягивается: круг остаётся кругом, шрифт — шрифтом. Это ровно та же модель,
что у сайта, где высота окна фиксирована, а вёрстка подстраивается под ширину.

```kotlin
class ProfilePage : Page() {
    override fun view(): View = Panel(
        width = Size.Fixed(viewport.width),    // весь экран
        height = Size.Fixed(viewport.height),  // всегда 1024
        children = listOf(/* … */),
    )
}
```

## Брейкпоинты

`viewport.size` — три класса, как в стилевых медиазапросах:

| Класс | Ширина | Кто это |
|---|---|---|
| `COMPACT` | < 1500 | 5:4, 4:3 |
| `REGULAR` | 1500…2100 | 16:10, 16:9 |
| `WIDE` | ≥ 2100 | 21:9 и шире |

```kotlin
Grid(columns = viewport.by(compact = 2, regular = 3, wide = 4), children = tiles)

val gutter = viewport.by(compact = Theme.SPACE_3, regular = Theme.SPACE_5)
```

Есть и счёт колонок по желаемой ширине карточки:

```kotlin
Grid(columns = viewport.columns(ideal = 260, min = 2, max = 5, gap = Theme.SPACE_3))
```

**Важное правило:** высота холста постоянна, поэтому на узком экране **нельзя** переносить
содержимое в лишние ряды — высота и так занята. Узкий экран означает *уже карточки*, а не
*больше рядов*. Ряды добавляют только тогда, когда одновременно что-то убирают.

## Ограничение ширины

Колонку держат в читаемой ширине так же, как в вебе — `max-width` с автоцентрированием:

```kotlin
Panel(
    width = Size.Fill,   // занять всё, что есть
    maxWidth = 1278,     // но не больше этого, остальное — поля по краям
    children = listOf(profile(), rightColumn()),
)
```

`maxWidth` / `maxHeight` / `minWidth` / `minHeight` есть у любой `Panel`. Когда места
больше лимита, панель встаёт по центру выделенного ей места — это `margin: 0 auto`.

## Безопасная полоса

Сервер не знает форму экрана наверняка (см. ниже), поэтому есть договорённость: всё, что
игрок читает и нажимает, должно помещаться в центральную полосу **`viewport.safeWidth`**
(4:3, то есть 1365 единиц). За её пределы выносят только фон, подсветку и украшения.

Тогда ошибка в форме экрана стоит красоты, а не работоспособности.

## Фон за краем холста

Ни одно окно не имеет в точности названный формат: заголовок окна и панель задач
отъедают часть высоты, и развёрнутое окно 1920×1080 на деле ближе к 1.89, чем к 1.78.
Разница видна как полоска мира вдоль края.

Поэтому фон страницы рисуется шире холста — на `Viewport.BLEED` единиц с каждой стороны:

```kotlin
class HomePage : Page() {
    // Красится первым и заходит за края; содержимое туда не попадает.
    override val bleed = listOf(Paint(0x000000, 0.97), pageTint)
}
```

Движок сам подставляет эти заливки под страницу при отрисовке. Туда выносят только цвет:
ни текста, ни кнопок за краем холста быть не должно.

## Откуда берётся форма экрана

Ванильный клиент её не присылает. В пакете настроек клиента есть язык, дальность прорисовки
и рука, которой игрок держит меч, — размера окна там нет, и запросить его нечем. Поэтому:

1. По умолчанию берётся `display.screen` из `config.yml` (по умолчанию `16:9`).
2. Игрок задаёт свою командой **`/vui screen`** — открывается страница с рамкой по краям
   холста: игрок жмёт форматы, пока рамка не сядет по краям экрана, и сразу видит результат.
3. На той же странице есть точная подгонка — «← уже» и «шире →» по 8 единиц: окно редко
   совпадает с форматом ровно, и двумя-тремя нажатиями рамка садится точно по краям.
4. Выбор запоминается в `plugins/VoidRpUI/screens.yml` навсегда.

Из своего кода:

```kotlin
plugin.screens.of(player)          // Viewport этого игрока
plugin.screens.set(player, Viewport.parse("4:3")!!)
plugin.screens.clear(player)       // вернуться к серверному значению
plugin.pages.refresh(player)       // перерисовать открытую страницу
```

## Проверка без игры

`./gradlew preview` рисует страницы в PNG, в том числе главную — в **каждом** формате
экрана: `build/preview/home-5x4.png`, `home-4x3.png`, `home-16x9.png`, `home-21x9.png`.
Рядом с каждым снимком лежит `.txt` с точной геометрией: что где оказалось и какого размера.

В тестах есть страховка, которая ловит самую частую ошибку адаптивной вёрстки:

```
./gradlew test --tests '*hangs off any screen*'
```

Она раскладывает каждую страницу на каждом формате экрана и падает, если хоть одна фигура
вышла за край. Свою страницу туда добавляют одной строкой.

## Что под капотом

Вершинный шейдер получает от клиента только положение пера и матрицу проекции. Из матрицы
он достаёт форму окна, высоту окна принимает за 1024 единицы и тем же масштабом считает
ширину. Координата x приезжает как расстояние от середины страницы — именно туда босс-бар
ставит перо, центрируя заголовок, — поэтому в шейдере не зашито никакой ширины: один и тот
же шейдер рисует страницу, свёрстанную под любой экран.
